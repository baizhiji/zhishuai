# 智枢AI 系统整体并发容量实测评估报告

**评估日期**：2026-09-01
**评估对象**：智枢AI SaaS 全系统（AI创作工厂 + 智能招聘 + 智能获客 + APK AI助手 + 推荐分享 + 横切能力）
**评估方法**：真实调用三云 API 读取配额 + 生产日志审计 + 代码调用链盘点
**前置说明**：上一份《research_report_system_capacity_2026.md》基于"端侧分布式推理"前提撰写，与真实架构（服务器转发三云 API）不符，本报告以实测为准。

---

## 执行摘要

在"香港 2核4G 单机 + 单 Node 进程 + 客户自带付费 Key（模型全开）+ 平台不兜底"的真实部署形态下，容量瓶颈已不在云配额（付费账号每客户独立且宽裕），而完全回到**服务器侧**。实测与建模结论：**系统可支撑约 200-500 个客户账号同时在线使用（其中约 100-200 个同时进行生成操作）、日活约 1500-2500**；对应约 100-200 个租户（按每租户 2-3 人同时在线）。达到上限的表现是"生成变慢、排队"，而不是崩溃或拒绝服务。另发现三个影响可用性的生产问题：全局限流中间件在反代场景下抛错（trust proxy 未配置）、pm2 进程 23 小时内重启 256 次、并发控制为"软偏好"（超限时仍会继续调用导致云侧 429 率上升）。

## 一、三云账号配额实测结果

### 探测方法

写探测脚本 `scripts/probe-quota.mjs` 部署到生产服务器，从数据库 ApiProvider/ApiKey 表读取实际 key、解密后真实调用三云 API：文本请求读取限流响应头、阿里百炼走官方配额接口 `GET /api/v1/quotas` 拉取全量 496 条配额记录、腾讯/火山做 5 并发温和试探。

### 1.1 阿里百炼（账号 501c7b7a，workspace ws-b3jiyrf1kc95iezh）

该账号实际持有 496 条模型配额记录，与系统生产使用的模型基本对应。按任务类型提取关键配额：

| 文本 | qwen3.7-max | 500 次/分钟，500,000 token/6小时 |
| 文本 | qwen-plus | 15,000 次/30分钟，250万 token/30小时 |
| 图片 | qwen-image-3.0 | 2 次/6分钟，并发 10，队列 200 |
| 图片 | qwen-image-3.0-pro | **5 次/60分钟**，并发 10，队列 200 |
| 图片 | qwen-image-max / 2.0-pro | 2 次/60分钟 |
| 图片 | z-image-turbo / qwen-image-plus | 2 次/1分钟 |
| 视频 | wan2.7-t2v / i2v / videoedit | 5 次/分钟，并发 5，队列 500 |
| 视频 | happyhorse 系列、pixverse 系列 | 5 次/分钟，并发 5 |
| 视频 | wan2.2-i2v-plus | 2 次/分钟，并发 2 |

**核心结论：上述为免费级测试账号的实测配额——文本宽裕（qwen3.8-max 每 6 小时 50 万 token），图片与 TTS 偏紧（qwen-image-3.0-pro 每小时 5 次、TTS 每分钟 3 次）。但按用户确认的运营模式（客户自带 Key、模型全开、付费档位），客户各自账号为付费配额，图片/TTS 限额高出一到两个数量级，第一节的免费配额仅用于说明"单 Key 上限"，不构成系统级容量约束（详见第三节）。**

### 1.2 腾讯云 TokenHub（账号 501c7b7a）

用 kimi-k3 实测：单请求 200 OK（约 2.3-2.7 秒），5 并发全 200 无任何限流响应头。TokenHub 不返回标准 x-ratelimit 头，配额在控制台配置（文本模型一般按 RPM/TPM 计），实测 5 并发未触发限制，实际可视为"控制台配额决定，当前用量远未触顶"。

### 1.3 火山方舟 Ark（账号 501c7b7a）

用 doubao-seed-2-1-pro 实测单请求 200 OK（约 5-6 秒，含推理）。Ark 同样不返回标准限流头，配额在控制台"配额管理"页按 RPM/TPM 配置。视频模型（可灵、混元视频、优图视频、Vidu 等）配额需控制台确认，API 无查询入口。

### 1.4 关键结构性发现：配额是"每用户每 Key"的，不是全局的

系统采用 BYOK（客户自带 Key）模式。数据库 ApiProvider 表（Admin 配置的系统兜底 Key）实测为 **0 条**，生产日志也显示只有用户 501c7b7a 的 key 在实际被使用（大量 `使用用户 501c7b7a...自行配置的 tokenhub API Key`）。这意味着：

- 上述阿里配额是**单个 key 的配额**，不是全系统配额；
- 每个配置了 key 的用户，各自在自己的账号配额内消耗；
- 系统真正的容量 = Σ(各用户 key 的配额)，但受服务器并发槽位封顶。

### 2.2 后台定时触发（隐性消耗）

| 调度器 | 周期 | 消耗方式 |
|---|---|---|
| recruitment-scheduler | 10 分钟（超时处理）+ 30 分钟（自动搜索） | 每个 active 搜索配置跑一次 matchCandidates；autoContact 开启时对全部匹配候选人批量生成沟通话术（每候选人 1 次 AI） |
| auto-comment（自动跟评） | 5 分钟扫描 | 到期任务 runAutoCommentTask 生成跟评内容（1-2 次 AI/任务） |

## 三、容量估算（付费 Key 全开 + 客户自带 Key 前提）

### 3.1 瓶颈分层（前提切换后的重估）

客户各配付费 Key、模型全开后，第一节实测的免费配额约束（图片 5 次/小时、TTS 3 次/分钟）不再构成系统级瓶颈——每个客户的配额在其付费账号内独立、且付费档位通常高出一到两个数量级。容量重新由以下三层决定：

1. **服务器 AI 并发槽位（真正的瓶颈）**：ai-model-router 全局单例，12 个模型（腾讯 6 + 阿里 4 + 火山 2），每模型 `maxConcurrentPerModel=10`。按任务类型候选分散：chat 类 3 个候选（30 槽位）、professional 类 4 个（40）、reasoning 类 2 个（20）、long_text 类 3 个（30）、vision 类 1 个（10）。**混合负载下有效文本并发约 40-60**。注意：该并发控制是"软偏好"——selectModel 按占用排序选最空闲模型，但全部超限时仍会返回模型继续调用，不会硬拒绝，因此高并发表现是延迟升高而非报错。
2. **服务器硬件**：2核4G，pm2 fork 单进程，实测基础内存仅 61MB。Node 单线程事件循环处理 IO 密集的 AI 转发富余；内存方面 50 并发 × 每连接 <5MB 缓冲 ≈ 300MB，2.8GB 可用内存充足。数据库 Prisma 连接池 + TDSQL-C 在百级 QPS 下无压力。
3. **应用限流**：AI 生成接口每用户 30 次/分钟、全局 100 次/分钟/IP。每用户 30 次/分钟远高于正常使用节奏，不构成"同时多少客户"的约束；但全局 100 次/分钟/IP 在 NAT 出口（多个客户共用同一公网 IP）时可能误伤，且该中间件当前因 trust proxy 缺陷在带 X-Forwarded-For 的请求上抛错（见第四节）。

### 3.2 文本类容量模型（核心）

并发槽位约 50（取混合负载中值），单次生成占用槽位时间：chat 类 3-10 秒、professional 类 10-30 秒、reasoning 类（DeepSeek V4 Pro 带推理）15-60 秒，平均约 15-20 秒。**吞吐 = 并发 / 平均耗时 ≈ 50 / 17 ≈ 2.9 次/秒 ≈ 170 次/分钟 ≈ 1 万次/小时**。

按真实用户行为折算：活跃客户平均每 60 秒发起一次生成操作、每次占槽 15-20 秒 → 每个活跃客户同时占用约 0.25-0.33 个槽位 → 50 槽位可同时承载约 **150-200 个正在操作的客户**。按高峰时段约 1/3 在线用户在操作估算，同时在线客户约 350-570。

### 3.3 多媒体类（付费配额下回到服务器侧）

**图片**：generateImage 直接调云 API（火山 seedream / 阿里 qwen-image），**不经过 aiModelRouter 并发控制**，无服务器端槽位限制，瓶颈只剩硬件 IO 等待（每张 10-30 秒）与付费配额（宽裕）。2核4G 下同时 30-50 张图片生成无压力。

**视频/音乐/数字人**：异步提交 + 轮询，提交瞬间只占用 1-2 秒的请求槽位，随后由任务轮询（每任务每 10-30 秒 1 次状态查询）消耗。服务器可同时挂几十到上百个视频任务，主要受云侧并发（付费账号通常数分钟数任务）与生成时长（2-10 分钟）影响，体感为排队而非容量崩溃。

**TTS**：同步、单次 10-60 秒，付费配额每分钟数十次，服务器侧与图片同理无硬槽位，同时几十路配音可行。

### 3.4 后台调度器的隐性消耗（付费前提下不再是瓶颈）

招聘调度每 30 分钟 + 跟评调度每 5 分钟：10 个 active 招聘配置、每个匹配 50 位候选人时约 500 次 AI 调用/30 分钟 ≈ 16 次/分钟，约占文本吞吐（170 次/分钟）的 9%。在付费配额宽裕、服务器吞吐富余的情况下可忽略；但客户数增长时调度量线性增长，200 个租户时约 100-300 次/分钟，会开始挤占用户流量，建议后续优化为分批/错峰。

### 3.5 综合数字（最终结论）

| 口径 | 数值 | 依据 |
|---|---|---|
| 同时进行生成操作的客户 | **100-200 个** | 50 文本槽位 × 每槽 3-4 个客户轮转 |
| 同时在线使用的客户（账号） | **200-500 个** | 按高峰 1/3-1/2 在线客户在操作 |
| 对应租户数 | **100-200 个** | 按每租户 2-3 个账号同时在线 |
| 日活（账号） | **1500-2500** | 按平均在线 30-60 分钟/日 |
| 文本吞吐 | 约 1 万次/小时 | 170 次/分钟 |
| 图片同时生成 | 30-50 张 | 无槽位限制，受硬件 IO 等待 |
| 视频并发任务 | 数十个 | 异步轮询，受生成时长排队 |

**直接回答"同时使用的客户可以有多少"：在客户各配付费 Key、模型全开的设定下，2核4G 单进程当前配置可支撑约 200-500 个账号同时在线（其中 100-200 个同时在进行生成操作）、对应 100-200 个租户、日活 1500-2500。达到上限的表现是生成明显变慢、排队时间拉长，但不会崩溃；超过约 500 同时在线后建议按"pm2 cluster 双进程 → 4核8G → 提高 maxConcurrentPerModel"顺序扩容，容量可再翻 2-4 倍。**

## 四、生产状态与隐患（实测发现）

1. **全局限流中间件缺陷（高优先级）**：生产日志持续出现 `express-rate-limit ERR_ERL_UNEXPECTED_X_FORWARDED_FOR: The 'X-Forwarded-For' header is set but the Express 'trust proxy' setting is false`。nginx 反代设置了 X-Forwarded-For，而 Express 未开启 `trust proxy`，导致 express-rate-limit 的 keyGenerator 抛异常。影响：应用自身限流（全局 100 次/分、AI 接口 30 次/分）在这些请求上失效甚至返回 500。修复方式：`app.set('trust proxy', 1)`（或 nginx 侧 `proxy_set_header X-Forwarded-For ""` 并关闭应用层限流的 XFF 依赖）。
2. **用户 Key 覆盖不足**：日志大量出现"未配置 AI 服务商 API Key""图像生成错误: 没有可用的 API 密钥"。当前只有测试账号 501c7b7a 配了 key。按你的定位（客户自带 Key、平台不兜底），交付时必须在每个租户开通流程中强制引导配置完整的付费模型 Key，否则该租户无法使用——这是比容量更紧迫的可用性约束。
3. **模型路由并发控制为软限制**：已实测确认 selectModel 在全部模型超限时仍会返回模型继续调用（不硬拒绝），因此高并发下的表现是延迟升高、云侧 429 率上升，而非明确报错。若需硬性保障，可在 selectModel 全超限时返回"系统繁忙"或改队列；并发计数为进程内 Map，pm2 cluster 多进程后各自独立，需改造为共享存储后才可安全扩容。
4. **pm2 进程 23 小时内重启 256 次**：生产 API 进程重启极其频繁。若为频繁部署所致可接受，但需确认是否存在 OOM/崩溃触发的重启（`pm2 status` 的 restart 数与当前 `uptime 23h` 结合判断），建议排查 pm2 日志中的非主动重启记录，避免容量还没到、稳定性先崩。

## 五、结论

按"客户自带付费 Key、模型全开、平台不兜底"的既定运营模式，容量评估的关键前提是：每个客户的云配额在其付费账号内独立且宽裕，故系统级容量由服务器侧决定。**最终结论：2核4G 单进程当前配置可支撑约 200-500 个账号同时在线使用、100-200 个同时进行生成操作、对应 100-200 个租户、日活约 1500-2500**；文本吞吐约 1 万次/小时，图片/视频/TTS 在付费配额下分别可支撑数十路并发。

扩容路径：客户数接近 500 账号时，先做 pm2 cluster 双进程（容量近翻倍，需同步把 aiModelRouter 并发计数改为共享存储、修复 trust proxy 限流缺陷），再升级 4核8G，最后按需提高 maxConcurrentPerModel。当前最大风险不在容量而在三个实测隐患：trust proxy 导致应用限流在反代场景抛错、pm2 高频重启待排查、客户 Key 未配置即无法使用——这三项修复的优先级高于任何扩容动作。

## 局限与后续

火山方舟与腾讯 TokenHub 的配额无 API 查询入口（响应头无 x-ratelimit，需控制台人工确认），本报告对两家的配额结论基于单发/5 并发实测与"无 429 记录"推断；可灵、混元视频、Vidu 等火山视频模型的付费配额同样需控制台核对。付费账号的具体 RPM/TPM 取决于客户购买档位，容量结论按"付费配额宽裕、非系统瓶颈"建模，若客户购买的是最低档付费套餐，图片/TTS 类配额可能重新成为该客户自己的体验瓶颈（与全局容量无关）。报告为保守估计，实际"同时在线"数字还受业务时段分布、单用户操作频率影响，建议上线后结合 pm2 日志中的实时并发与云控制台用量做校准。
