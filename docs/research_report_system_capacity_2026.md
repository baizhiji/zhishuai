# 智枢AI 系统容量全景报告（2026-08-14 修正版）

> **本文档为修正版**。上一版错误地基于"服务器集中式 SaaS"架构（2核4G CVM 跑 Playwright、服务器内存决定并发）分析容量，与产品实际架构前提不符。
> **正确架构前提**：系统做成**电脑安装版客户端**（每台客户电脑本地跑浏览器自动化），**APK 端依靠手机自身算力**（端侧执行），服务器仅做调度/记账/数据中转。

---

## 一、架构前提（容量分析的出发点）

本报告的容量分析建立在端侧分布式架构上，与"服务器集中式"有本质区别：

| 维度 | 服务器集中式（错误前提） | 端侧分布式（正确前提） |
|------|------------------------|----------------------|
| 浏览器自动化执行位置 | 服务器（CVM 跑 Playwright） | 客户电脑安装版客户端本地 |
| AI 算力位置 | 服务器代客户调用模型 | APK 端手机本地算力 / 客户 Key 直连模型平台 |
| 数字人视频生成位置 | 服务器（GPU 渲染，内存风险） | 端侧（电脑 GPU 本地渲染 / 手机本地 / 客户 Key 调云端视频 API） |
| 服务器角色 | 算力承担者（瓶颈所在） | 纯调度中心（任务分发、限额记账、安全校验、结果回传、文件中转） |
| 容量扩展方式 | 服务器升配/多节点 | 增加客户端设备数，天然线性扩展 |
| 服务器 2核4G 是否够用 | 是当前瓶颈 | 绰绰有余，反而最轻松的一层 |

在这个架构下，**算力不再有任何"单点瓶颈"，容量 = 客户端数量 × 单机能力**，是分布式并行，而不是服务器共享算力池。

## 二、三层容量重新分析（修正后）

### 第 1 层：AI 话术生成（APK 手机本地算力 / 客户 Key 直连）

- 端侧模型受手机芯片约束：中端手机（骁龙 7 系/天玑 8000）跑 1-3B 量化模型约 5-20 token/s，旗舰（骁龙 8Gen3/A 系列）跑 7B 量化约 10-30 token/s。
- 单条跟评话术 50-100 字 ≈ 生成 25-50 token，单条生成约 5-15 秒。手机本地算力完全够用。
- 若走客户 Key 直连（阿里百炼/火山方舟），生成延迟 1-3 秒/条，容量由客户购买的 API 配额决定，与平台服务器无关。
- **结论：生成层容量远大于投放需求。** 单账号每天仅需 16-24 条话术，手机本地模型几分钟即可产完当天全部话术，**生成层不是瓶颈**。

### 第 2 层：评论投放执行（电脑安装版客户端本地）

- 每台客户电脑本地跑浏览器自动化（Playwright），单台普通配置（4核8G）可并行 2-4 个浏览器实例。
- 容量 = 客户端设备数 × 单机并行能力。100 台客户电脑 = 100 台并行执行器，天然分布式。
- 服务器完全不参与执行，**不存在服务器内存/CPU 瓶颈**。
- 2核4G 服务器只承担调度：每台客户端每 10-20 分钟心跳一次拉取任务，几百台设备轮询也仅几十 QPS，负载极低。

### 数字人视频生成（端侧执行，已确认）

用户已确认数字人视频生成也在端侧执行，不在服务器。容量分析如下：

- **电脑安装版（主力）**：数字人渲染是"预生成、非实时"任务。中端独显（RTX 3060 级）跑 2D 数字人（SadTalker/LivePortrait 类）实时率约 0.3-1.0，即生成 60 秒视频需 20-60 秒，单机一小时可预生成 30-90 条短视频素材。生成后可批量缓存，投放时直接取用，**不占实时算力**。
- **APK 手机端**：手机本地跑轻量数字人（30 秒短视频）约需 1-5 分钟/条，适合低频场景（每天几条）完全够用；高频场景建议走电脑端或客户 Key 直连云端视频 API。
- **无服务器内存/GPU 约束**：上一版担心的"同步等待内存风险"随执行位置移到端侧而消除。服务器既不渲染也不等待渲染进程，只接收最终产物。
- **端侧生成后的唯一服务器成本是文件的中转与分发**：30-60 秒 720P 视频约 10-30MB。若平台要求视频回传服务器再由各端下载，则带宽成为唯一新关注点（见第四节第 4 点）。

### 第 3 层：平台风控限额（与架构无关，真正的天花板）

- 抖音/快手：4 条/时、16 条/天；小红书：6 条/时、24 条/天（`server/src/services/comment-delivery.service.ts` 的 `PLATFORM_LIMITS`）。
- 新号分级：7 天内 30% 配额、5 条封顶；失败率 ≥20% 且发送 >5 条触发 24h 熔断。
- **这一层与架构无关**——无论算力在服务器还是端侧，平台单账号限额都是 16-24 条/天，无法突破。
- 扩容手段只有一条：**增加账号数**（多账号矩阵），而不是提升算力。

## 三、修正后的真实容量结论

| 层 | 容量决定者 | 上限 | 扩容手段 |
|----|-----------|------|---------|
| AI 话术生成 | 手机本地算力 / 客户 Key 配额 | 远大于投放需求，非瓶颈 | 无需扩容 |
| 评论投放执行 | 客户端设备数 × 单机并行 | 随客户端数线性扩展，无单点瓶颈 | 增加客户端/账号 |
| 数字人视频生成 | 端侧 GPU/手机本地/客户 Key（预生成批量任务） | 单机一小时 30-90 条素材，非瓶颈 | 增加端侧设备；带宽走对象存储 |
| 平台风控限额 | 平台风控规则 | 单账号 16-24 条/天 | 增加账号数，不能硬提 |
| 服务器调度 | 2核4G 纯调度负载 | 几百台客户端轮询绰绰有余 | 基本无需扩容 |

**核心判断（修正）**：
1. 端侧架构下**服务器不再是容量瓶颈**，反而是全系统最轻松的一层。上一版报告担心的"8-12 并发内存瓶颈""maxConcurrentPerModel 接近 90"在端侧架构下**不成立**——那些是服务器集中式的问题，端侧架构里服务器根本不跑浏览器、不代客户生成。
2. **真正的容量天花板从头到尾只有一个：平台风控的单账号日限额（16-24 条）**，这个结论任何架构下都成立。
3. 端侧架构的容量扩展逻辑极简单：**1 台设备 + 1 个账号 = 16-24 条/天**。客户要放量，就是"加设备、加账号"，全部由客户侧解决，平台侧 2核4G 服务器不用动。

## 四、端侧架构下服务器侧仅剩的关注点

1. **调度稳定性**：客户端心跳/任务拉取的 API 要做到幂等、可重试，几百台客户端同时掉线重连时不雪崩（现有 `express-rate-limit` 已兜底，建议调度接口单独放宽限流）。
2. **账号数据安全**：客户端本地持有平台 cookies，服务器只存加密后的账号元数据与限额记账。cookies 的加解密要在端侧完成，服务器不落明文。
3. **限额记账一致性**：服务器仍是所有账号限额的"唯一账本"（防客户端本地篡改），这个职责不变，且 2核4G 完全扛得住（单账号每天最多 24 条记账写入）。
4. **视频文件的中转带宽（数字人端侧生成后的新增项）**：30-60 秒 720P 视频约 10-30MB/条。若视频需经服务器中转分发，香港 CVM 固定带宽（常见 1-5Mbps）会成为唯一实质瓶颈——单条 20MB 视频在 5Mbps 带宽下上传约需 30 秒。**对策**：客户端直传对象存储（COS/OSS），服务器只分发 URL（秒级、几乎零带宽成本）；或按流量计费带宽规避固定带宽上限。此点只影响数字人高频场景，不影响评论投放主链路（纯文本，每条约 1KB）。

## 五、上一版报告的错误点对照（自查）

| 上版结论（错误） | 修正 |
|-----------------|------|
| 服务器内存瓶颈 8-12 并发，账号破百才接近瓶颈 | 端侧架构下服务器不跑浏览器，无此瓶颈 |
